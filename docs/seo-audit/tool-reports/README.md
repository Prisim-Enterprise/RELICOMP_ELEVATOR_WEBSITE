## Reading the local reports

Both local runs were built with `NEXT_PUBLIC_SITE_URL` set to the local origin so the
sitemap would emit crawlable local URLs. **Delete `.next` before that rebuild.** The
12 Nov run did not, and two findings in it are artefacts of that rather than defects:

- **"Canonical points elsewhere" on `/` and `/contact`.** Those two routes were
  unchanged, so Next served them from the incremental cache with their production
  canonical, and the tool saw a canonical that did not match the localhost origin it
  was auditing. The live run reports no canonical findings at all, and the 13 Nov run
  — done after `rm -rf .next` — does not reproduce them. Production was never affected.

The live report also flags `/privacy-policy` and `/terms-of-service` for **incomplete
Open Graph** and **no JSON-LD**. Both are fixed in the local build and absent from its
report — independent confirmation of that fix, which is recorded in
`../remediation-2026-11-12.md`.

## GEO 60 → 100 (13 November)

GEO 60 was a cap, not a tally. The six categories came to 80 raw **with AI crawler
configuration already counted at 0 of 20**, and the rubric's rule 2 then capped the
total at 60 because an unanswered AI policy counts as a GEO blocker. The blocker was
a single item: `robots.txt` took no *explicit* position on AI crawlers. Everything was
already allowed through the catch-all `*` group, which the tool's own crawler matrix
confirmed.

`app/robots.txt/route.ts` now states the policy — allow all, split into AI-training,
AI-search and user-triggered blocks, with a `Content-Signal:` line and the IETF AIPREF
token. That earned the missing 20 and lifted the cap, so GEO went to 100 in one step.
**No crawler's access changed**; 22 AI crawlers simply moved from matching `*` to
matching a group that names them.

An earlier note in this file estimated the gain at "60 to roughly 80". That was wrong:
it double-counted the 20 points as already awarded. The move was the full 40.
